## 1. 프로젝트 한 줄 정의

> **매주 월·금 오전 6시(KST), 최근 수신 메일을 자동 수집·분류해 "한눈에 보는 트리아지 대시보드"를 만들고 본인 이메일로 발송하는 개인 자동화 시스템.**

- **만드는 사람**: Ssuub (문수빈)
- **해결하는 문제**: 수신함의 약 80%가 뉴스레터·광고. "처리할 메일"이 노이즈에 묻힘 → 주 2회 정해진 시각에 **확인필요 메일만 위로 끌어올린 요약**을 받아 빠르게 트리아지.
- **형태**: n8n 스케줄 워크플로(서버 자동 실행) + 자기완결형 HTML 대시보드(오프라인 열람).

## 3. 확정된 핵심 사양

새 채팅이 다시 도출할 필요 없도록, 이미 합의된 스펙을 고정해 둡니다.

### 3-1. 수집 시간 창 (월·금 두 실행이 빈틈·중복 없이 맞물림, 모두 KST)

| 실행 | 트리거 | 수집 범위 | 의미 | cron |
|---|---|---|---|---|
| **월요일** | 월 06:00 | 지난 금 06:00 → 월 06:00 | 주말분(금 낮·토·일·월 새벽) | `0 6 * * 1` |
| **금요일** | 금 06:00 | 월 06:00 → 금 06:00 | 주중분(월·화·수·목·금 새벽) | `0 6 * * 5` |

- 통합 cron: `0 6 * * 1,5` / 타임존 `Asia/Seoul`
- **상대값(`newer_than`) 금지** — 실행 시점에 06:00 경계를 epoch로 계산해 정확히 자른다.

### 3-2. Gmail 조회

- 쿼리: `in:inbox` + `receivedAfter`/`receivedBefore`(ISO datetime, 초 단위 정확)
- **수신만**: `labelIds`에 `INBOX` 있는 것만. `SENT`만 있는 항목은 제외.

### 3-3. 메일 레코드 스키마

```js
{ from, email, subj, snip, date /*ISO UTC*/, cat, prio, unread }
```

| 필드 | 규칙 |
|---|---|
| `from` | 발신자 표시명(정리된 라벨) |
| `email` | 실제 발신 주소 |
| `subj` | 제목(트래킹 문자열 제거) |
| `snip` | snippet 한 문장 요약(≤160자, 원문 덤프 금지) |
| `date` | `internalDate` 또는 Date 헤더 → ISO |
| `cat` | 아래 6분류 |
| `prio` | `high`/`mid`/`low` |
| `unread` | `labelIds`에 `UNREAD` 포함 여부 |

### 3-4. 분류·우선순위 기준 (rubric)

| `cat` | 의미 | 기본 `prio` |
|---|---|---|
| `action` | 답장·조치 필요(개인 메일, CI 실패, 마감) — **유일하게 high** | high |
| `account` | 계정·약관·정책 공지 | mid/low |
| `study` | 강의·녹화본·연구 알림 | mid/low |
| `outlier` | 기회·제안·채용(반복 多, `(×N)`으로 압축) | low |
| `security` | 로그인·접근 알림(대개 본인 유발) | low |
| `news` | 뉴스레터·광고·다이제스트(노이즈 버킷, 최대 다수) | low |

- **핵심 원칙**: 노이즈는 패턴으로 쉽게 잡힌다 → "노이즈가 아닌 것"은 곧 확인필요에 가깝다. 따라서 뉴스레터/보안/공지/학습/기회 패턴에 **안 걸리는 메일은 `action`/`high`로 격상**(안전한 방향의 오탐 허용).
- **개인화**: 본인 프로젝트와 연결된 메일(내 레포 CI 실패, 지원 단체 회신 등)은 일반 패턴보다 우선해 `action`으로.

### 3-5. 디자인 시스템 (현재 대시보드)

- 라이트 트리아지 톤: 배경 `#eef0f3` · 패널 `#fff` · 본문 `#161a22`
- 우선순위/분류 색: action `#c0392b` · account `#1f7a8c` · study `#6a4c93` · outlier `#b8860b` · security `#9aa0ab` · news `#8a93a3`
- 메타·숫자는 모노스페이스, 시간은 **KST 자동 변환**
- (선택) 본인 K-SURE 디자인 시스템(다크네이비 `#0d1b2a` + 에메랄드 `#00e5a0`)으로 리스킨 가능 — 원하면 새 채팅에서 요청.

## 4. 아키텍처 (n8n 5노드)

```
[Schedule  0 6 * * 1,5  TZ=Asia/Seoul]
      │
      ▼
[Code: Compute Window]   요일 판별 → after/before(ISO·epoch) 계산, runType·rangeLabel·selfEmail 출력
      │
      ▼
[Gmail: 수신 조회]        getAll, simple=false, filters: q=in:inbox + receivedAfter/Before
      │
      ▼
[Code: Build Dashboard]  레코드화 → 분류·정렬(action 최상단) → ①인터랙티브 HTML(첨부) ②정적 요약(본문)
      │
      ▼
[Gmail: 발송(본인)]       to=selfEmail, subject=요약, body=정적표(HTML), attach=대시보드.html
```

- **이메일 본문** = JS 없는 정적 요약표(어떤 메일앱에서도 표시). **첨부** = 검색·필터 되는 인터랙티브 대시보드.
- 분류 로직은 n8n Code 노드에 **키워드 규칙**으로 이식(런타임에 LLM 없음).
- HTML 템플릿은 워크플로에 **base64로 내장**(외부 파일 의존 0).

## 5. 남은 작업 (백로그)

우선순위 순. 새 채팅에서 이 중 하나를 골라 진행하면 됩니다.

1. **[배포] n8n 적용 & 활성화** — 임포트 → Gmail OAuth2 연결(조회·발송 2노드) → `selfEmail` 확인 → 수동 테스트 → Active ON.
   - 전제: n8n 호스트가 06:00에 켜져 있어야 함(가능하면 **항상 켜진 NAS**에 호스팅).
2. **[정밀화] 분류를 Gemini 노드로 업그레이드** — 키워드 규칙 대신 §3-4 rubric을 LLM에 적용해 오탐 제거(본인 Gemini 키 재활용).
3. **[이중화] Telegram 알림 추가** — 이메일 + UniAssist 봇 동시 발송(`확인필요 N건` 푸시 + 링크).
4. **[열람성] NAS 정적 호스팅 연동** — 첨부 대신 NAS에 `inbox-YYYYMMDD.html` 저장, 메일엔 Tailscale 링크만 → 폰에서 바로 열기.
5. **[운영] 안정화** — 0건일 때 처리(이미 됨), 실패 알림, 주간 로그 보관, 중복 발신자 압축 룰 강화.

## 6. 환경·제약

- **실행기**: n8n (이미 보유). Coupang 리뷰봇 등 n8n+Playwright+Gemini 경험 있음.
- **알림 채널**: 이메일(본인 발송) 확정. 기본 수신 주소 `soobin7612@gmail.com`(워크플로 `Compute Window` 노드 하단에서 변경).
- **호스팅 후보**: Synology NAS(Docker, 항상 켜짐) ↔ 노트북. **NAS 권장**(노트북 꺼지면 06:00 트리거 누락).
- **개발 환경**: Windows + Synology NAS + venv, Tailscale 다기기 접근.
- **주의**: n8n Gmail 발송 본문이 raw로 보이면 메시지 타입을 HTML로 지정.

## 7. 작업 규칙(Claude에게)

> 프로젝트 커스텀 인스트럭션에 넣을 내용.

- 답변 언어 **한국어**, 핵심 먼저·근거는 뒤. 표·리스트 적극 활용.
- 문서·코드·설계물은 **전문적·깔끔한 톤(이모지 제외)**, 일반 대화·아이디어 탐색은 친절한 톤.
- 개발 작업 시 본인 스킬 **`dev-project-workflow`** 방법론을 따른다(설계 문서 → 합류 지점 기반 테스트 → Git 워크플로, 드리프트 감지 리마인드 포함).
- 메일 자동화 작업에는 **`email-inbox-dashboard`**, 회신 작성에는 **`email-reply-addressing`** 스킬을 사용한다.
- 코드 변경은 **수정 이유 → 변경 → 검증(드라이런/문법검사)** 순으로 제시.
- 확정 사양(§3)을 임의로 바꾸지 말 것. 변경이 필요하면 먼저 제안하고 합의.
